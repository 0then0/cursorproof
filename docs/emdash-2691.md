# EmDash plugin storage validation

This lab checks CursorProof against a historical cursor pagination defect in
[EmDash](https://github.com/emdash-cms/emdash) using EmDash's real
`PluginStorageRepository` before and after the fix. It is an independent
TypeScript target next to the [Django REST framework example](drf-regression.md).

It is a historical check, not a claim about current EmDash. The issue is closed
and fixed. The lab validates that CursorProof detects that defect through its
public CLI and passes the repaired contract. It does not prove EmDash correct and
it does not test EmDash's CMS, admin UI or public HTTP API.

## Sources and pinned versions

- Issue: [emdash-cms/emdash#2691](https://github.com/emdash-cms/emdash/issues/2691).
  `query()` with `orderBy` returned duplicate pages and skipped older rows. The
  reporter exported 150 records as 199 rows with 99 duplicates and 50 missing.
- Fix: [emdash-cms/emdash#2699](https://github.com/emdash-cms/emdash/pull/2699),
  squash-merged as `01855cb9cb8fd748170e462e391925533b226fcd`.
- Before: `37e08b013cbd87fe57963a10c31b64091862f975`, the first parent of the
  squash commit.
- After: `01855cb9cb8fd748170e462e391925533b226fcd`.

The two snapshots differ in one executed file,
`packages/core/src/database/repositories/plugin-storage.ts`. The lab records
SHA-256 digests of every upstream file that was executed. Full commits, source
tree digests and tool versions are in
[provenance.json](../labs/emdash-2691/provenance.json) and the run summary.

EmDash is MIT licensed. The lab downloads source archives into a disposable
directory when you prepare it and does not commit or redistribute upstream code.

### The contract change

Before the fix, `query()` sorted by an expression over the JSON `data` column
(`orderBy: { createdAt: "desc" }` means `data.createdAt`, not the internal
`created_at` column) but built the seek predicate from the internal `created_at`
and `id` columns. The cursor holds `created_at` and `id` of the last row. The
two keys were unrelated, so page 2 repeated rows or skipped them. The reported
descending case is the visible one. Ascending order also failed whenever the sort
field disagreed with insertion order.

The fix, as described in the pull request:

- The seek compares the same expressions that `ORDER BY` uses.
- `id` is appended as a tiebreaker in the direction of the first sort field.
- A `NULL` sort value ranks last ascending and first descending, on any dialect.
- A cursor with `orderBy` fields in mixed directions throws `StorageQueryError`.
- The default path without `orderBy` and the `limit` clamp of 100 are unchanged.

## What is tested

The lab imports three unmodified upstream modules from the snapshot:
`db/node-sqlite-compat.ts`, `database/migrations/runner.ts` and
`database/repositories/plugin-storage.ts`. `PluginStorageRepository` is not a
public package export of `emdash`, so a test-only HTTP wrapper calls it. This is
a bounded harness around an internal API. It is not an EmDash REST endpoint, and
its URL, parameters and response shape are not EmDash's.

Each run uses a new SQLite database created by EmDash's own migrations and filled
through `repository.put()`. The wrapper is [server.mjs](../labs/emdash-2691/harness/server.mjs):

- `GET /query?orderBy=&direction=&limit=&cursor=` parses the four declared
  parameters, calls `repository.query()` once and returns `items`, `cursor` and
  `hasMore`. Undeclared parameters are rejected with 400.
- `GET /healthz` reports readiness after migrations and fixture loading.
- It does not compute cursors, edit predicates or ordering, remove duplicates,
  add rows or clamp limits. The only representation choice is that the terminal
  page's absent cursor (`undefined`) is written as JSON `null`.

`harness_check.py` verifies this: on the same database file it walks pages over
HTTP and by calling the repository directly from Node.js, and requires identical
pages and cursors, including the repeated pages the pre-fix code returns.

Upstream's TypeScript uses constructor parameter properties, which Node.js type
stripping rejects, so [ts-loader.mjs](../labs/emdash-2691/harness/ts-loader.mjs)
transpiles each `.ts` file with the pinned `typescript` package (no type
checking) and resolves `./x.js` to `./x.ts`. The harness dependencies are
`kysely 0.29.2`, the version both snapshots lock, and `typescript 5.9.3`, locked in
`package-lock.json`. Upstream's own dependency tree and install scripts are not used.

## Fixture and oracle

[fixture.json](../labs/emdash-2691/fixture.json) is generated by
[fixture.py](../labs/emdash-2691/fixture.py). It has 150 documents `sub-001` to
`sub-150`, inserted in id order, with three indexed fields:

- `createdAt`: 150 unique timestamps that increase with insertion order, like
  form submissions. This is the reported scenario.
- `score`: 50 values, each shared by three records and unrelated to insertion
  order. Tie groups straddle the page edges at 10, 50 and 100.
- `note`: explicit JSON `null` on every fifth record, otherwise 17 distinct values.

The `note` scenarios use explicit `null`. CursorProof requires every ordering path
to exist in the response, so it cannot express a document that omits the key. The
repository also ranks the SQL `NULL` of a JSON null the same way.

[oracle.py](../labs/emdash-2691/oracle.py) reads the SQLite file read-only and
checks that its documents equal the fixture. It prints the expected ids without
the repository or any cursor. Its rules:

- Numbers compare numerically and strings by Unicode code point. The fixed UTC
  timestamps therefore compare chronologically.
- A null sorts after every value ascending and before every value descending.
- Equal sort values order by id, by code point, in the same direction.
- With no `orderBy` the order is the stored `(created_at, id)`.

The fixture file has SHA-256
`38eda8967aeeec7a7a41ca51be615103590326d30935b54cb065347140815e21`. Expected
order digests per scenario are in the run summary.

## Scenarios

Each [config](../labs/emdash-2691/configs) uses token pagination, page sizes
10, 50 and 100, `max_pages: 60`, `max_items: 3000` and an ordered command oracle.
The lab does not treat the repository's silent clamp at 100 as a finding.

- `default-order`: no `orderBy`; control that holds before and after the fix.
- `created-asc`: ascending on an aligned field; control that holds both ways.
- `created-desc`: the reported newest-first export.
- `score-asc`, `score-desc`: uncorrelated sort field with ties at page edges.
- `note-asc`, `note-desc`: explicit nulls, last ascending and first descending.

## Run it

Requirements: Python 3.10 or newer with CursorProof installed, Node.js and npm.
Upstream requires Node.js 22.16 or newer; the lab was run only on 26.13.0.
Preparation is the only networked step and installs nothing from upstream. From
the repository root:

```sh
uv build --out-dir /tmp/cursorproof-build
uv venv /tmp/cursorproof-lab-env
uv export --locked --no-dev --no-hashes --no-emit-project -o /tmp/cursorproof-lab-req.txt
uv pip install --python /tmp/cursorproof-lab-env/bin/python -r /tmp/cursorproof-lab-req.txt
uv pip install --python /tmp/cursorproof-lab-env/bin/python --no-deps /tmp/cursorproof-build/cursorproof-*.whl
```

```sh
python3 labs/emdash-2691/prepare.py --workdir /tmp/cursorproof-emdash-2691
```

`prepare.py` downloads the two source archives, extracts only
`packages/core/src` and a few metadata files without running anything, checks the
tree digests in `provenance.json`, and runs `npm ci --ignore-scripts` for the
harness lockfile. Then, with no network:

```sh
/tmp/cursorproof-lab-env/bin/python labs/emdash-2691/run_lab.py \
  --workdir /tmp/cursorproof-emdash-2691 --output /tmp/emdash-2691-evidence
/tmp/cursorproof-lab-env/bin/python labs/emdash-2691/harness_check.py \
  --workdir /tmp/cursorproof-emdash-2691
```

`run_lab.py` starts the real repository for each version, three times, each on a
fresh database and an ephemeral loopback port, runs `cursorproof check`, `run`
and `replay` for every scenario, and writes `summary.json`, the upstream file
digests and representative traces. It exits 1 if an expectation or an offline
replay fails, after saving what it observed.

To try one scenario by hand, start the wrapper and use a committed config:

```sh
export EMDASH_LAB_DEPS=/tmp/cursorproof-emdash-2691/harness-deps
export EMDASH_LAB_DB=/tmp/emdash-lab-manual.sqlite3
node --import labs/emdash-2691/harness/ts-loader.mjs labs/emdash-2691/harness/server.mjs \
  --snapshot /tmp/cursorproof-emdash-2691/snapshots/37e08b013cbd87fe57963a10c31b64091862f975 \
  --db "$EMDASH_LAB_DB" --fixture labs/emdash-2691/fixture.json --port 8791
```

```sh
cursorproof run labs/emdash-2691/configs/created-desc.yml --repro /tmp/created-desc-trace.json
```

Remove `$EMDASH_LAB_DB` between runs; the wrapper refuses an existing file.

## Results

The checked-in [run summary](../labs/emdash-2691/evidence/summary.json) was
recorded with the CursorProof 0.2.0 wheel built from this checkout (no change to
`src/`), Python 3.13.18, Node.js 26.13.0 and npm 11.20.0 on macOS arm64.

Before the fix, `created-desc` returns two pages at every page size. At page
size 100 it observes 199 rows, 100 distinct ids, 99 duplicates and 50 missing
ids, the numbers from the issue. CursorProof reports CP002 duplicates, CP004
ordering violations, CP003 missing records against the oracle and CP009 for
streams that differ between page sizes. The other uncorrelated scenarios fail the
same way: for example `score-asc` at page size 100 observes 218 rows and 109
distinct ids. `note-asc` at page size 10 stops after 30 distinct ids with no
duplicates, which a duplicate check alone would not catch.

The two controls, `default-order` and `created-asc`, pass before and after the
fix. After the fix every scenario passes at all three page sizes: 150 distinct
ids in the exact oracle order, no duplicates, no gaps and exit 0.

All three repetitions produced the same signatures for every scenario and
version. Timestamps and cursor bytes differ between databases and are not
compared. The harness and database were stopped and removed after each
repetition; the summary records the exit state, closed port and removed file.
An interrupted run (SIGTERM) leaves no process or temporary database behind.

## Replay the evidence

Offline replay uses only CursorProof and the saved traces:

```sh
uv run --no-sync python labs/emdash-2691/replay_evidence.py
uv run --no-sync cursorproof replay labs/emdash-2691/evidence/traces/before-created-desc.json
uv run --no-sync cursorproof replay labs/emdash-2691/evidence/traces/after-created-desc.json
```

The first exits 1 with duplicate, ordering and missing-item findings; the second
exits 0. Replay re-analyses the recorded observations. It does not execute EmDash
again, so it confirms the analysis of the stored traces, not the behavior of the
code. `tests/test_emdash_2691_lab.py` checks the fixture, the oracle rules, the
evidence summary and these replays without Node.js.

## Isolation and limits

- The wrapper binds only `127.0.0.1` and serves GET requests. It stops after
  `--max-requests` (default 2000) requests or `--max-lifetime-seconds` (default
  300). `run_lab.py` sets 1500 and 600 and passes `--exit-on-stdin-close`, so an
  interrupted runner cannot leave a wrapper behind.
- CursorProof limits each traversal to 60 pages and 3000 items; subprocesses have
  deadlines. Output is bounded by the fixture.
- Databases live in a temporary directory removed on success, failure and
  cancellation. No shared database, remote service or installed CMS is used.
- Not tested: PostgreSQL, the `limit` clamp above 100, mixed-direction sorting,
  documents that omit the sort key, concurrent writes, or any later EmDash.
- The results cover these two commits, SQLite via `node:sqlite`, static data and
  page sizes 10, 50 and 100.
